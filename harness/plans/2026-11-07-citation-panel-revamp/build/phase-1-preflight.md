# R1 前置核對與基線

- **後置條件**：確認分支、HEAD、工作樹與工具都符合計劃的基線，並把可沿用的測試基線、來源與限制記錄在 build-log；不要求為建立基線重新跑完整套件。基線不符時，先修正後續階段的描述，再繼續。
- **涵蓋**：G8（後續所有回歸檢查都以這裡的基線為比較對象）。
- **相依**：無。
- **標準與政策**：[GOALS.md](../GOALS.md)、[PLANS.md](../PLANS.md)。

## 步驟

| 步驟 | 工作 | 必要檢查 |
|---|---|---|
| R1-S1 | **唯讀核對**。逐項確認：<br>1. 分支是 `GUI`，記錄 HEAD。<br>2. 本計劃的檔案都已提交；如果沒有，補一個 `docs(plan): …` commit，phase 檔用 `git add -f`。<br>3. `git status` 中與本計劃無關的未追蹤或已修改檔案：只記錄，不動。<br>4. PLANS「基線」列出的程式位置仍然成立，必要時用 `grep -n` 確認；行號可能有些微位移，但同樣的程式碼必須存在。<br>5. zip 的 SHA-256 與 PLANS 記載的值相同；解壓到 `$TMPDIR` 下新建的空目錄後，`sha256sum -c manifest.sha256` 全部通過，`__version__` 是 `1.1.5`。<br>6. Conda `app` 中的 `poetry`、`npm`、`cargo`、`pandoc` 都可以執行。 | 每一項的指令與結果都寫進 build-log。有任何一項不符時，判斷影響哪些階段，修改那些階段檔後再繼續；如果 zip 的雜湊值不符，R3 標為 Blocked，其他階段照常進行 |
| R1-S2 | **核對既有測試基線**。先讀 PLANS 的歷史紀錄，找出對應的 build-log、命令、程式版本與環境；必要時用唯讀 `git show` 讀取已歸檔紀錄。比較現況，標示哪些證據仍可沿用。無適用紀錄時記為「基線未知」，只選必要且便宜的相關測試補查；R1 不跑完整 pytest、npm 或 cargo 套件。 | 記錄證據來源、版本、當時結果、可沿用範圍與限制；新增的局部檢查另記結果與耗時，不冒充完整基線。既有失敗列明測試名稱與原因，不修復無關問題；可繼續不受影響的工作，但 G8／R6 仍要求必要自動檢查全部通過，不能僅因「不新增失敗」就標為 Complete |

完成 R1-S1 和 R1-S2 後，各自 commit（只提交 build-log，以及必要時修改的計劃檔）。

## 交付給後續階段

可沿用的基線及其來源、適用範圍、未知項目與已知失敗。R2–R6 用它們辨識回歸；完整套件留至 R6 各跑一次，基線未知或既有失敗不降低最終標準。
