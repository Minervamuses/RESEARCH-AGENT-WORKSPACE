# K6 詰問評估框架

- **後置條件**：有案例格式、合成示範案例、評估腳本與報告格式；腳本預設不呼叫付費模型，加明確旗標才連 OpenRouter；以假模型跑通；使用說明寫好，使用者可放入自己的真實段落後自行執行。
- **涵蓋**：G3。
- **相依**：K5（腳本走 `grill` 的實際路徑，並依 SKILL.md 的還原標記與引用格式做機械檢查）。
- **輸入**：GOALS U2、S4、「未解決、但不阻塞本計劃的事項」；S1 一「還沒解決的」。

## 嚴格限制

執行者在本階段不得以真實模型執行腳本，也不得啟動會連 OpenRouter 的任何程式。所有驗證用假模型。

## 規格

1. **案例格式**（建議 JSON）：每個案例有 `id`；`kind`（`flawed` 或 `clean`，表示案例作者目前的標註，不是完整真值）；`source`（`synthetic` 或 `real`）；`document`（整份上下文文字，Markdown）；`selection`（`document` 中逐字存在的段落）；`known_issues`（每條有 `id`、原文引用、說明；`clean` 案例為空，但不表示禁止發現其他有效問題）；`author_turns`（腳本化的作者回應，每條描述預設要回應的具體質疑，並有 `type`：`rephrase`、`supply_step`、`valid_rebuttal`，及條件式預期 `maintain`、`request_write_in`、`withdraw`）。預期只有在實際質疑與回應對得上時才適用，由使用者判斷，不由腳本自動認定。
2. **示範案例**：建議放 `app/tests/fixtures/grill/cases.example.json`。至少 3 個 `flawed`（例如推論跳步、把假定當事實、拿不適用的概念當理由，各一，僅為示例，不構成錯誤分類表）與 2 個 `clean`，全部標為 `synthetic`，內容由執行者自行撰寫，不取自使用者的論文資料夾。檔頭或說明寫清楚「示範用，不能代表真實論文的測試結果」。
3. **腳本**（建議 `app/scripts/grill_eval.py`）：
   - 參數：`--cases <路徑>`、`--out <目錄>`、`--live`、`--max-rounds <n>`。
   - 走和編輯器相同的生產路徑（桌面服務的文件回合：開啟文件、`documentContext` 範圍等於 `selection`、輸入含 `@grill` 與對應 `skillReferences`），讓遮蔽與快照說明都被涵蓋；模型以可注入的工廠建立，測試注入假模型。
   - 桌面服務預設會載入 MCP（`agent/desktop/service.py` 約第 341 行 `_load_mcp = True`，在約第 1622 行由 `load_mcp` 參數設定）。假模型模式與所有測試一律不載入 MCP，不啟動 web search MCP 或瀏覽器；`--live` 模式在開跑前印出 MCP 是否啟用（建議預設不啟用，另以明確參數開啟）。
   - 沒有 `--live` 時拒絕建立真實模型，印出原因並以非零結束碼結束。有 `--live` 時，開跑前印出案例數與最多模型回合數（案例數 × (1 + 作者回應數)，上限 `--max-rounds`），提醒會產生 OpenRouter 費用。
   - 文件放在 `--out` 下的暫存工作專案中，不碰案例原檔；結束後確認文件內容未被改動。
4. **報告**（每個案例一份 Markdown＋一份 JSON，加一份總表）：每一輪的模型回覆全文與呼叫過的工具名稱；機械記錄——有無還原段、發現所引原文是否逐字存在於 `selection` 或 `document`、模型如何表達通過或資料不足、首次宣告通過的輪次或達上限、全程有無 `document_edit` 呼叫、文件是否未變。這些只反映可觀察格式與流程，不能證明理解或質疑正確。另留人工觀察表：還原是否忠於原文的限定與強度；每條質疑及其理由是否成立；每個已知問題是否被找到；有無標註之外的有效問題或硬挑；作者回應是否針對實際質疑，以及適用時模型後續處理是否合理。適用性初始留待人工填寫，可記「適用／此輪不適用」並附理由；不適用時不按預寫預期評判是否變軟或拒絕撤回。不得自動判定語意命中、把未標註發現一律當誤報，或產生單一詰問品質分數。
5. **使用說明**（建議 `app/skills/grill/README.md`）：案例格式、如何放入自己的真實段落（建議放在 repo 外或不提交的位置）、執行指令、成本提醒、如何讀報告。研究觀察聚焦於還原是否忠實、質疑是否成立、能否發現有意義的問題、是否硬挑，以及回應對題時的多輪處理與回合數；不從固定標題推定模型內部思考過程。腳本回應不對題時標記此輪不適用，必要時後續回合也註明此限制；使用者可在桌面以 `@grill` 針對實際質疑接續回應並另附對話紀錄，不與固定腳本回放混成同一評估。不要求新增自動分支、語意評分模型或互動評估框架。

## 步驟

| 步驟 | 工作 | 必要檢查 |
|---|---|---|
| K6-S1 | 案例格式、格式驗證與示範案例 | 測試：示範案例通過格式驗證；`selection` 不在 `document` 中、`kind` 與 `known_issues` 矛盾、未知的 `type` 都被拒絕並給出清楚訊息 |
| K6-S2 | 腳本與報告 | 假模型測試：沒有 `--live` 時不建立真實模型且結束碼非零（以注入檢查確認沒有建立 OpenRouter 用戶端）；假模型執行時 MCP 未載入（檢查服務的 MCP 設定或診斷結果）；假模型對一個 `flawed` 案例回覆含還原段與一條逐字引用、一條非逐字引用，報告正確標出兩者；`clean` 案例第一輪有範圍的通過被記錄，資料不足的回覆不被機械判成研究失敗；作者回應依序送出、輪數正確；全程無 `document_edit`、文件未變；報告保留上述人工欄位且適用性預設待填，不自動按 `expected` 判成語意通過／失敗；以示範填表確認可記此輪不適用及未標註的有效問題 |
| K6-S3 | 使用說明，並以假模型對示範案例完整跑一次；示範報告展示人工觀察欄位與不適用的填寫方式 | 把假模型產生的示範報告存到 `evidence/K6-S3/`，在 build-log 明寫「假模型輸出與示範填表，只證明流程，並非真實研究結果」 |

各步驟各自 commit。

## 交付給後續階段

腳本、示範案例、使用說明與示範報告。K8 的最終彙報附上使用者自行跑真實測試的指令與成本提醒。
