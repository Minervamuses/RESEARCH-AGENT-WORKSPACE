# 第 09 步：結構化 progress 與 Bash approval bridge

## 目標

把現有node/tool progress安全送到UI，並在取得明確批准後，讓GUI版`bash`維持「每次呼叫都由使用者核准」的既有政策。

## 重要批准閘門

Bash approval需要沿`ChatSession → build_graph → tool inventory → bash tool`注入provider，預計觸及超過三個production files。正式實作前必須：

1. 列出確切檔案與介面。
2. 說明為何維持non-TTY auto-deny不足以達成GUI功能。
3. 取得使用者明確批准。

若未批准，安全fallback是保留non-TTY auto-deny，UI明確標示「GUI目前不支援bash批准」；不可用PTY解析prompt繞過。

## Progress adapter

現有callback為`(node_name, new_messages)`且在graph stream同步呼叫。GUI adapter應：

- callback內只做快速、non-blocking enqueue。
- 後台consumer把LangChain message轉安全DTO。
- AI tool call → `tool.started`。
- ToolMessage → `tool.finished`或`tool.failed`。
- Agent node無tool call → `stage.changed(finalizing)`。
- 不送完整content、args、artifact、response metadata。
- Queue有界；若UI太慢，合併重複stage或記diagnostic，不阻塞graph。

Extended candidates目前callback沒有可靠candidate ID；第一版顯示generic extended activity，不猜測candidate attribution。若要精準candidate trace，另做明確core callback改造與測試。

## Approval provider抽象

建議最小介面：

```text
approve(command, description, command_timeout) -> bool
```

兩個implementation：

- CLI provider：保留現有TTY prompt與default deny。
- Desktop provider：建立immutable pending request，送`approval.required` event，等待`approval.resolve`。

不能把approval decision搬到React後直接執行command；真正`subprocess.run`仍在Python bash tool內。

## Desktop approval request

DTO包含：

- opaque `approvalId`。
- parent `requestId`／turn ID。
- 完整command（唯讀）。
- model提供的description。
- execution timeout上限。
- backend產生時間與approval expiry。

Frontend response只傳`approvalId`與`approved: bool`；不可回傳修改後command。

## Default-deny規則

- Modal關閉、Escape、backend disconnect、turn failure、shutdown → deny。
- Approval timeout → deny（獨立於command execution timeout）。
- Unknown、duplicate、expired、already-resolved ID → reject。
- Late approval永遠不能復活command。
- 同時多個bash calls可在backend各有ID；UI以queue逐一顯示，不能把一個yes套用全部。

## UI modal

必須顯示：

- `Why` description。
- 完整command，可水平scroll/copy，不可編輯。
- cwd固定為app root。
- timeout。
- `拒絕`為primary/default focused action，`執行`為明確secondary危險action。
- 明文提醒`bash`沒有filesystem sandbox，會以目前使用者權限執行。

不要加入「本次session全部允許」或remember approval。

## Policy不變條件

- GUI provider只替換人機approval通道，不改tool access resolution。
- Skill/proposer不允許bash時，PolicyToolNode仍先拒絕，不能產生approval modal。
- `shell=True`、cwd、timeout、output truncation等既有行為若非本step直接必要，不順便重構。
- CLI與pytest non-TTY仍維持既有auto-deny測試。

## Tests

### Python

- CLI TTY yes/no/EOF與non-TTY deny不退化。
- Desktop approve/deny/timeout/late/duplicate。
- Approval response不能替換command。
- Policy-denied call不發approval。
- Backend shutdown解開所有waiters並deny。
- 多pending approvals不串錯turn。

### Rust/TypeScript

- Approval event依parent request correlation。
- Modal default focus與keyboard deny。
- Backend crash自動關modal並標示not executed。
- UI不在log/transcript保存command，除非使用者主動展開當次activity。

## 驗收條件

- 未按`執行`的command絕不執行。
- 每個實際執行command都有同一immutable approval ID與exact command紀錄。
- GUI frontend沒有shell capability。
- Existing CLI/non-TTY behavior與tests保持相容。
- 若此step未實作，GUI對bash的限制在Chat與Diagnostics都清楚可見。
