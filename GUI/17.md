# 第 17 步：以代表性真實案例做端到端驗收

## 目標

測試真正user-visible output與資料結果，而不是只看「event完成」或unit test通過。先在temp data/state完成，再對使用者目前資料做只讀確認。

## 執行前批准

逐項告知並取得批准：

- 是否允許一次真實OpenRouter chat call。
- 是否允許一次folder tagging call（可產生多個request）。
- 是否允許citation providers live network call。
- 是否允許實際bash command（只選無副作用read-only command）。
- 是否允許完整pytest/npm/cargo suite與預估時間。

未批准的live case用fake fixture替代，報告不得宣稱real provider驗收通過。

## 隔離策略

- Mutation案例設temporary `KMS_STORE_DIR`、citation output、extension roots、plan logs或test config。
- 不刪／移動`app/store`、`cite`、`app/plan_logs`。
- 不修改Conda secret設定。
- 完成後只移除本次明確建立的temp directory；先驗證resolved path。

## Case 1：啟動與Diagnostics

1. 從Conda `app`啟動Tauri。
2. 確認Linux/Python/Conda/app root/protocol。
3. 確認secret只顯示boolean。
4. 模擬MCP unavailable，session仍可ready/degraded。
5. 模擬wrong env，backend fail-fast且UI給正確指引。

成功證據：backend/session狀態清楚、沒有orphan process。

## Case 2：Normal chat與工具活動

1. 建立session，送一個簡短問題。
2. 若用fake model，安排一次RAG tool call再final。
3. UI只顯示tool name/status，finalized Markdown正確。
4. Running時第二turn被拒絕。
5. 關閉app，驗證flush呼叫成功。

若批准live call，再用一個低成本、無mutation問題驗證真實OpenRouter output；記錄實際model/時間，不宣稱performance guarantee。

## Case 3：Plan mode

1. 切Plan並取得path。
2. 完成一turn。
3. 驗證Markdown含`do_not_index: true`、user/tool/assistant block。
4. 確認沒有寫入chat-history store（用temp history fake或既有test證據）。
5. 離開Plan，snapshot更新。

## Case 4：Thinking/Skill/Citation policy

- Extended可在配置完整時啟用；Citation active時被disable。
- 啟用Citation自動回Normal。
- 切其他skill清session registry但不刪bundle。
- Citation gate-blocked fixture只顯示safe final answer。
- 不把existing bundles列成active sources。

Live citation search/save只有獲批准才做；使用專用temp citation output。

## Case 5：Knowledge read

先只讀目前資料確認baseline：

- `app/store/raw.json`目前有1 chunk/1 pid。
- `folder_meta.json`目前不存在，因此Overview應是empty而非error。
- Ollama ready時search；offline時Overview/Documents仍可開。
- Context target與window正確。

不把這些數量寫成永久產品假設。

## Case 6：Ingest/sync/prune（temp store）

1. 建立兩三個小UTF-8 fixture files。
2. Single-file ingest，確認pid/chunks與progress。
3. Folder ingest用fake tagger/embedder；若批准再做最小live version。
4. Search/overview refresh。
5. 移除temp source file，Sync顯示store-not-disk。
6. Prune preview。
7. 先改變source/diff，確認stale preview拒絕。
8. 新preview後apply，核對actual deleted list。

故意failure一次以驗證`partialWritePossible`訊息，但不要破壞真實store。

## Case 7：Extensions（temp roots）

1. 建立test Skill/MCP bundle。
2. Status不呼叫model。
3. Fake model preview列正確authoritative change。
4. 未批准MCP得到pending approval。
5. 批准exact hash後apply，revision增加、restart required。
6. Restart後loaded catalog/family才更新。
7. 修改drop-in後舊preview被拒絕。

不在此case嘗試修cross-process race。

## Case 8：Bash approval（若第09步完成）

- Deny：command未執行。
- Timeout/close/crash：command未執行。
- Approve exact harmless read-only command（例如顯示cwd），result returned。
- Modified/late approval拒絕。
- Frontend沒有shell API。

## Case 9：Shutdown/crash

- Idle graceful close。
- Flush failure→app不自動退出。
- Active turn close→等待/return，不誤稱cancel。
- Force quit顯示data warning並清child。
- Unexpected child crash→pending failed、可手動restart、新session。

## 驗收報告格式

每case記錄：

- Preconditions。
- Exact command/user actions。
- Expected vs actual user-visible result。
- Written paths／provider calls。
- Pass/fail與remaining limitation。

不要只貼大量terminal log；保留最小必要證據。

## 驗收條件

- 所有第一版範圍至少一個representative pass。
- Persistent outcome與UI宣稱一致。
- Live calls/real store access完全符合批准範圍。
- 未通過case不以unit test替代宣稱成功。
- 完成後停止，不順手做optional polish。
