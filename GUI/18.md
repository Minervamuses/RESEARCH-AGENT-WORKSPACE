## 第一交付形態（建議）

在既有workspace與Conda `app`環境中執行：

```bash
conda run -n app npm --prefix app/desktop run tauri dev
```

實際script可能需要從`app/desktop`執行，以scaffold驗證結果為準。重點是：

- Tauri、Node、Python都在Linux。
- Python從同一Conda env繼承。
- Backend cwd固定為`app/`。
- WSLg顯示Linuxwindow。

另提供production build command，但第一版不承諾雙擊desktop launcher：

```bash
cd app/desktop
conda run -n app npm run tauri build
```

Built binary仍需在能解析Conda `app` Python的環境啟動。

## Linux bundle的限制

Tauri可建立deb/AppImage等Linux格式：[Tauri distribution](https://v2.tauri.app/distribute/)。但本project backend仍依賴外部Conda env、Ollama與可能的MCP binaries。

官方AppImage說明也指出GUI app不一定繼承shell dotfile PATH：[AppImage](https://v2.tauri.app/distribute/appimage/)。因此不能假設使用者從檔案管理器雙擊後能找到`python`。

若真的需要bundle，先在下列方案中另做決策：

### A. 外部Conda env + explicit launcher

- 最符合現況、最低變更。
- Launcher需要可設定的Conda executable/env，不硬編碼個人path。
- Bundle不是standalone；文件必須坦白。

### B. Bundle Python executable sidecar

- 需PyInstaller/Nuitka等新dependency、target triple build、Chroma/native libs/MCP/Ollama integration驗證。
- 體積與維護成本高。
- Tauri externalBin要求target-specific executable。
- 只有明確portable distribution需求時才批准，不能當第一版預設。

### C. Bundle整個Conda runtime

- 更重，更新與license/size複雜。
- 不符合目前單人local project的最小需求，預設拒絕。

## 不在本計劃自動執行的delivery工作

- App signing、auto updater、store publishing。
- CI cross-build matrix。

- Telemetry/crash upload。
- Commit/push/release。

這些全部需要新的具體目標與批准。

## Windows native ↔ WSL 的獨立決策

若使用者日後要求Windows `.exe`，必須另寫方案處理：

- `wsl.exe` process lifecycle與distro selection。
- Windows/WSL path translation與file picker。
- Windows Tauri UI和Linux Python不同cwd/env。
- App close/orphan WSL process。
- Ollama/MCP到底在Windows或WSL。
- Citation `fcntl` lock與Linux-only persistence。
- Windows code signing/bundle。

在此決策前，不能把現在的Linux GUI聲稱為Windows app。

每一項先有demonstrated user need，再做最小方案；持久格式變更需特別批准與migration/rollback計劃。
